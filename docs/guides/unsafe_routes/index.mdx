# Using unsafe routes for access beyond overlay hosts

Hosts on a Nebula network may need to reach devices that cannot run Nebula, such as printers, physical access control
systems, or proprietary devices. If such devices are on a subnet reachable by one of the Nebula hosts, that host can act
as a subnet gateway, forwarding traffic from other Nebula hosts to the subnet devices.

This guide explains how to configure Nebula’s `unsafe_routes` feature to route traffic through the subnet gateway to the
devices that cannot run Nebula.

The `unsafe_routes` feature also allows you to [route `0.0.0.0/0`](#route-00000-using-unsafe-routes) (full-tunnel
routing), which enables a Nebula host with a public IP to act as an internet gateway for other overlay hosts.

:::note

This guide covers configuring a Linux host as the subnet gateway.

:::

```text
 NEBULA OVERLAY NETWORK   ░   SUBNET (HOME LAN)
                          ░
  ┌──────────────┐        ░
  │ Roaming Host │────┐   ░
  └──────────────┘    │   ░
                      │   ░
    ┌────────────┐    │   ░
    │ Lighthouse │────┤   ░
    └────────────┘    │   ░
                      │   ░
            (nebula1) │   ░
                  ┌───┴────────────┐
                  │ Subnet Gateway │
                  └───────────┬────┘
                          ░   │ (eth0)
                          ░   │
                          ░   │    ┌─────────┐
                          ░   └────│ Printer │
                          ░        └─────────┘
```

## Prerequisites

_Read the [Quick Start](/docs/guides/quick-start/) guide to learn how to create a basic Nebula overlay network._

To complete this guide, you will need the following:

1.  A working basic Nebula overlay network with a lighthouse and at least two hosts:
    - A **roaming host** running Linux, macOS, or Windows that needs access to the subnet devices
    - The **subnet gateway** running Linux, macOS, or Windows that will forward traffic from the overlay network to the
      subnet using `unsafe_routes`
1.  CA with the `nebula-cert` binary able to sign host certificates with additional metadata required for
    `unsafe_routes`
1.  The `ca.key` and `ca.crt` files for the Nebula overlay network
1.  Root access to the roaming host
1.  Root access to the subnet gateway

> This guide assumes that you have the directory for the `nebula` and `nebula-cert` binaries in your `$PATH`.

In the directory containing your CA cert, run:

```sh
nebula-cert print -path ca.crt
```

If `unsafeNetworks` (formerly `-subnets`) is not specified or if it contains the subnets that you want to access, you
are good to go. If it already contains subnets and they do not include the ones you need, you will have to create all
certificates from scratch.

Here's an example of a CA generated without specifying `unsafeNetworks`:

```sh
# For more focused output, the -json flag is added and the result is piped to jq
nebula-cert print -json -path ca.crt | jq .details
{
  "groups": null,
  "isCa": true,
  "issuer": "",
  "name": "BK Labs",
  "networks": null,
  "notAfter": "2027-09-23T10:24:58+08:00",
  "notBefore": "2026-09-23T10:24:58+08:00",
  "unsafeNetworks": null
}
```

## Example network

To illustrate how `unsafe_routes` works in practice, this guide uses an example scenario with the hostnames, IP
addresses, and subnets provided below.

### Nebula overlay network (Internet)

This is the overlay network with hosts running Nebula. Let's choose a common overlay network subnet `10.0.0.0/24` with
the IP range `10.0.0.1 – 10.0.0.254`.

The `nebula-roaming` host in this example has Internet access but is not on the home LAN.

| Overlay host IP | Overlay hostname | Description                                                          |
| --------------- | ---------------- | -------------------------------------------------------------------- |
| `10.0.0.1`      | `lighthouse`     | Nebula lighthouse                                                    |
| `10.0.0.5`      | `subnet-gateway` | Overlay host routing traffic between overlay and subnet              |
| `10.0.0.11`     | `nebula-roaming` | Roaming host that needs access to the printer _via_ `subnet-gateway` |

### Subnet (Home LAN)

This is the subnet on which a roaming host needs to access devices. Let's choose a common LAN subnet `192.168.1.0/24`
with the IP range `192.168.1.1` – `192.168.1.254`.

| Subnet device IP | Overlay hostname | Description                                    |
| ---------------- | ---------------- | ---------------------------------------------- |
| `192.168.1.5`    | `subnet-gateway` | Overlay host routing traffic to subnet devices |
| `192.168.1.25`   | (none)           | Printer that cannot run Nebula                 |

## How to add unsafe routes

With your Nebula overlay network and subnet up and running, add unsafe routes following the steps below.

On the subnet gateway:

- [Step 1. Subnet gateway: Add unsafeNetworks to the certificate](#step-1-subnet-gateway-add-unsafenetworks-to-the-certificate)
- [Step 2. Subnet gateway: Configure Nebula firewall](#step-2-subnet-gateway-configure-nebula-firewall)
- [Step 3. Subnet gateway: Configure traffic routing](#step-3-subnet-gateway-configure-traffic-routing)

On a client host:

- [Step 4. Roaming host: Configure traffic routing](#step-4-roaming-host-configure-traffic-routing)

Using the setup in [Example network](#example-network), this guide will show you how to configure the roaming host
(`nebula-roaming`, `10.0.0.11`) to route traffic through the subnet gateway (`subnet-gateway`, `10.0.0.5` and
`192.168.1.5`) to reach the printer on the home LAN from anywhere.

## Step 1. Subnet gateway: Add unsafeNetworks to the certificate

On your CA host, go to the directory containing your `ca.crt` and `ca.key`, then sign a new cert for the subnet gateway
with subnets you want to route:

```sh
nebula-cert sign -name 'subnet-gateway' -networks '10.0.0.5/24' -unsafe-networks '192.168.1.0/24'
```

Inspect the new certificate to confirm that `unsafeNetworks` is now correctly set to the home LAN subnet.

```json
nebula-cert print -json -path subnet-gateway.crt | jq .details
{
  "groups": null,
  "isCa": false,
  "issuer": "57903a07e52a8f5464636aeccb1942560324dcd1f6c4f0457d77b00372b5d9f2",
  "name": "subnet-gateway",
  "networks": [
    "10.0.0.5/24"
  ],
  "notAfter": "2027-09-23T10:24:57+08:00",
  "notBefore": "2026-09-29T11:24:07+08:00",
  "unsafeNetworks": [
    "192.168.1.0/24"
  ]
}
```

Next, copy the new host cert and key over to the subnet gateway:

```sh
# Replace user with your ssh username
scp subnet-gateway.crt subnet-gateway.key user@10.0.0.5:~/
```

After copying these files, login to your subnet gateway host and replace your existing cert and key files (commonly
stored in `/etc/nebula`) with the updated files. It's also a good practice to make sure that the key file is only
readable by root. If you change existing file paths for the cert and key, don't forget to update them in your Nebula
`config.yml` file.

## Step 2. Subnet gateway: Configure Nebula firewall

Besides adding the subnet to the cert's `unsafeNetworks` field, you need to add separate firewall rules on your subnet
gateway to regulate inbound traffic to your subnet from other overlay hosts. For this, add an inbound firewall rule with
[local_cidr](/docs/config/firewall/#firewallinbound) for subnet devices and ports that you need to reach.

To access the printer on the home LAN, you need to add an inbound firewall rule to allow TCP port 631 on
`192.168.1.0/24` (depending on your printer, you may need to include additional ports). On the subnet gateway, edit the
Nebula configuration file (commonly located at `/etc/nebula/config.yml`) and add the following to existing firewall
rules:

```yaml
firewall:
  inbound:
    - port: 631
      host: any
      proto: tcp
      local_cidr: 192.168.1.25/32
```

However, the easiest way to configure the firewall is to allow any port or protocol. In this case, on the subnet
gateway, add the following to existing firewall rules:

```yaml
firewall:
  inbound:
    - port: any
      host: any
      proto: any
      local_cidr: 192.168.1.0/24
```

At this point we're finished configuring the Nebula-specific components on the subnet gateway. If Nebula is running,
it's a good idea to restart it to validate that the configuration file, cert, and key are set up correctly.

```sh
$ sudo nebula -config /etc/nebula/config.yml

msg="Firewall rule added" firewallRule="map[caName: caSha: cidr: direction:incoming endPort:0 groups:[] host:any localCidr: proto:0 startPort:0]"
msg="Firewall rule added" firewallRule="map[caName: caSha: cidr: direction:incoming endPort:0 groups:[] host:any localCidr:192.168.1.0/24 proto:0 startPort:0]"
msg="Firewall started" firewallHashes=SHA:bec58c30ae0bd0463ff56a5fe9a75a21dc0253a44e3dcbe00e0d70dfb2fbe782,FNV:1666660931
msg=listening addr=[::]:4242
msg="Main HostMap created" preferredRanges=[]
msg="punchy enabled"
msg="Loaded send_recv_error config" sendRecvError=always
```

You can either leave Nebula running in the background or stop it while completing the next step on the subnet gateway.

## Step 3. Subnet gateway: Configure traffic routing

Now, you need to configure traffic routing on Linux. First, allow packet forwarding between network interfaces. Then,
configure the firewall to do packet routing and NAT.

### Enable IP forwarding

Typically, packet forwarding is not enabled by default, and the respective kernel parameter is set to `0`:

```sh
$ sudo sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 0
```

You can update this variable at runtime as follows:

```sh
$ sudo sysctl -w net.ipv4.ip_forward=1
net.ipv4.ip_forward = 1
```

:::note

This change will be lost upon reboot.

To make it persist across reboots, add `net.ipv4.ip_forward = 1` to `/etc/sysctl.conf`.

:::

### Configure packet routing

Now that packet forwarding is enabled, you need to add a few firewall rules. First, the subnet gateway needs to route
packets between Nebula and local network interfaces. Second, it needs to do network address translation (NAT).

Below you can find generic steps to configure the following:

- [ufw](#ufw)
- [nftables](#nftables)
- [iptables](#iptables)

:::note

Please note that the exact steps will depend on your firewall state.

For example, if your subnet gateway host runs Docker, its forward and postrouting rules may affect the routing rules
proposed below.

:::

#### ufw

First, allow packet routing between the Nebula interface and the local network interface:<br /> _(Replace network
interfaces (`nebula1`, `eth0`) and subnets with your actual ones)_

```sh
sudo ufw route allow in on nebula1 out on eth0 from 10.0.0.0/24 to 192.168.1.0/24
sudo ufw reload
```

Confirm the new rule is active:

```sh
$ sudo ufw status
Status: active

To                         Action      From
--                         ------      ----
192.168.1.0/24 on eth0  ALLOW FWD   10.0.0.0/24 on nebula1
```

Next, enable NAT to masquerade outgoing packets.

Open `/etc/ufw/before.rules` and add the NAT configuration block at the top of the file (before any \*filter block):

```sh
# NAT table rules
*nat
:POSTROUTING ACCEPT [0:0]

# flush all existing POSTROUTING rules in the nat table to avoid duplicates on reload
-F POSTROUTING

# 10.0.0.0/24 is the Nebula network, 192.168.1.0/24 is the route CIDR
-A POSTROUTING -s 10.0.0.0/24 -d 192.168.1.0/24 -j MASQUERADE

# don't delete the 'COMMIT' line or these nat table rules won't be processed
COMMIT
```

Reload UFW to apply the NAT configuration:

```sh
sudo ufw reload
```

#### nftables

Create a new nftables configuration (e.g., `/etc/nftables/nebula.conf`). Configure the packet forwarding chain and then
the NAT postrouting chain:<br /> _(Replace network interfaces (`nebula1`, `eth0`) and subnets with your actual ones)_

```sh
table ip nebula_routing
delete table ip nebula_routing
table ip nebula_routing {
  chain forward {
    type filter hook forward priority filter; policy accept;
    iifname nebula1 oifname eth0 ip saddr 10.0.0.0/24 ip daddr 192.168.1.0/24 counter accept
    iifname eth0 oifname nebula1 ip saddr 192.168.1.0/24 ip daddr 10.0.0.0/24 ct state established,related counter accept
  }

  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 10.0.0.0/24 ip daddr 192.168.1.0/24 counter masquerade
  }
}
```

To load the rules, run:

```sh
sudo nft -f /etc/nftables/nebula.conf
```

To verify that the rules have taken effect, you can run:

```
$ sudo nft list table nebula_routing
table ip nebula_routing {
	chain forward {
		type filter hook forward priority filter; policy accept;
		iifname "nebula1" oifname "eth0" ip saddr 10.0.0.0/24 ip daddr 192.168.1.0/24 counter packets 6 bytes 504 accept
		iifname "eth0" oifname "nebula1" ip saddr 192.168.1.0/24 ip daddr 10.0.0.0/24 ct state established,related counter packets 6 bytes 504 accept
	}

	chain postrouting {
		type nat hook postrouting priority srcnat; policy accept;
		ip saddr 10.0.0.0/24 ip daddr 192.168.1.0/24 counter packets 2 bytes 168 masquerade
	}
}
```

:::note

These changes will be lost upon reboot.

To make them persist across reboots, include this file in your main `/etc/nftables.conf` by adding the following line to
it:

```sh
include "/etc/nftables/nebula.conf"
```

:::

#### iptables

First, allow packet routing between the Nebula interface and the local network interface:<br /> _(Replace network
interfaces (`nebula1`, `eth0`) and subnets with your actual ones)_

```sh
sudo iptables -I FORWARD 1 nebula1 -o eth0 -s 10.0.0.0/24 -d 192.168.1.0/24 -j ACCEPT
sudo iptables -I FORWARD 2 eth0 -o nebula1 -s 192.168.1.0/24 -d 10.0.0.0/24 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

Next, add the NAT rule to masquerade outgoing traffic:

```sh
sudo iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -d 192.168.1.0/24 -j MASQUERADE
```

Once complete, confirm the forwarding rules are active:

```sh
$ sudo iptables -L FORWARD -v -n
Chain FORWARD (policy DROP 135 packets, 10404 bytes)
 pkts bytes target     prot opt in     out     source               destination
  524   76K ACCEPT     0    --  nebula1 eth0    10.0.0.0/24         192.168.1.0/24
 1034 1469K ACCEPT     0    --  eth0    nebula1 192.168.1.0/24      10.0.0.0/24          ctstate RELATED,ESTABLISHED
```

Then verify the NAT rule:

```sh
$ sudo iptables -t nat -L POSTROUTING -v -n
Chain POSTROUTING (policy ACCEPT 0 packets, 0 bytes)
 pkts bytes target     prot opt in     out     source               destination
    0     0 MASQUERADE  0    --  *      *       10.0.0.0/24          192.168.1.0/24
```

You may see additional rules listed depending on your host and if other services (such as Docker) have modified
iptables.

:::note

These changes will be lost upon reboot.

To make them persist across reboots, you need to run additional commands (e.g. `iptables-save`) depending on your Linux
distribution.

:::

## Step 4. Roaming host: Configure traffic routing

_The subnet gateway host is set up. We are almost there!_

The final step is to configure the overlay network hosts to use `unsafe_routes` to route the traffic destined for the
subnet devices through the subnet gateway.

On `nebula-roaming`, make sure you have the following in the `tun` config section:

```yaml
tun:
  drop_local_broadcast: true
  drop_multicast: true
  unsafe_routes:
    - route: 192.168.1.0/24
      via: 10.0.0.5
```

Run Nebula with the new configuration:

```sh
$ sudo nebula -config /etc/nebula/config.yml
# To improve readability, each output line has been redacted as follows:
# time=2026-09-29T04:04:06.476Z level=INFO msg="..." redacted to msg="..."

msg="Firewall rule added" firewallRule="map[caName: caSha: cidr: direction:incoming endPort:0 groups:[] host:any localCidr: proto:0 startPort:0]"
msg="Firewall started" firewallHashes=SHA:498215dec4e5687a2353f51c10838c113bd1af35ef72b8e8c9f536986ada5417,FNV:2782948616
msg=listening addr=[::]:4242

msg="punchy enabled"
msg="Loaded send_recv_error config" sendRecvError=always
msg="Loaded accept_recv_error config" acceptRecvError=always

msg="Handshake message received" vpnAddrs=[10.0.0.1] from=<lighthouse-public-ip>:4242 certName=lighthouse certVersion=2 fingerprint=<...> issuer=<...> initiatorIndex=2523598458 responderIndex=1344867621 handshake="map[stage:2 style:ix_psk0]" durationNs=59967190 sentCachedPackets=1
```

As you can see in `msg="Added route"`, the unsafe route is being used.

Now you should be able to successfully ping any host on the subnet from your roaming host and access subnet devices:

- **Ping working?** Great! Go ahead and add that printer, map file shares, and SSH to any host on the home LAN.
- **Ping not working?** If both your roaming host and subnet gateway are behind NAT, they might have issues pinging each
  other. In this case, try using [punchy](/docs/config/punchy/) or [relay](/docs/config/relay/). For details, see
  [NAT traversal and firewalls](/docs/guides/nat-traversal/).

Add the same `unsafe_routes` section to other overlay hosts that need access to subnet devices.

## Tips

### Avoid IP conflicts with underlay networks

When you are running Nebula with `unsafe_routes` the host's OS will forward all traffic destined for the unsafe route to
Nebula. This might cause a local IP conflict if your underlay network happens to use the same IP range as the subnet
specified in your `unsafe_routes` configuration.

### Use unsafe routes with Mobile Nebula

After you've successfully completed the steps above, you can also access your unsafe routes from a device running Mobile
Nebula on [Android](https://play.google.com/store/apps/details?id=net.defined.mobile_nebula) or
[iOS](https://apps.apple.com/us/app/mobile-nebula/id1509587936). For this, launch the app and configure it as follows:

1. Tap the site you want to configure
1. Tap _Configuration_ → _Advanced_ → _Unsafe routes_
1. Tap _Add a new route_ and enter the same `route` and `via` values that you used in
   [Step 4](#step-4-roaming-host-configure-traffic-routing)
1. Tap _Save_

If connected, disconnect from the site. Now, connect again and try to access one of the hosts only accessible using
`unsafe_routes`. You should see a new line in your Mobile Nebula logs.

`level=warning msg="Adding UNSAFE Route" route=192.168.1.0/24 via=10.0.0.5`

### Route `0.0.0.0/0` using unsafe routes

A Nebula host with a public IP can act as an internet gateway for other hosts in the overlay network. When
[setting up full-tunnel routing](#how-to-add-unsafe-routes), keep in mind the specifics outlined below.

```text
LOCAL REGION INTERNET     ░     REMOTE REGION INTERNET
                          ░
        .....................................
        :      NEBULA OVERLAY NETWORK       :
        :                                   :
 ┌──────┴───────┐                  ┌────────┴─────────┐
 │ Roaming Host │─────────────────►│ Internet Gateway │───────►
 └──────┬───────┘        (nebula1) └────────┬─────────┘ (eth0)
        :                                   :
        :  ┌────────────┐                   :
        :  │ Lighthouse │                   :
        :  └────────────┘                   :
        :...................................:
                          ░
                          ░
```

On the internet gateway host, ensure that:

- The certificate's `unsafeNetworks` field includes `0.0.0.0/0`
- Inbound Nebula firewall rules cover `local_cidr` for `0.0.0.0/0`
- System firewall rules for forwarding and NAT/masquerading do not contain destination restrictions (such as
  `-d 192.168.1.0/24`)

On overlay hosts, configuring full-tunnel routing through an internet gateway host varies in complexity depending on the
operating system.

Mobile Nebula [Android](https://play.google.com/store/apps/details?id=net.defined.mobile_nebula) and
[iOS](https://apps.apple.com/us/app/mobile-nebula/id1509587936) apps handle `0.0.0.0/0` correctly if you follow the
guidelines in [Use unsafe routes with Mobile Nebula](#use-unsafe-routes-with-mobile-nebula).

On non-mobile Nebula hosts, routing `0.0.0.0/0` creates a routing loop. To maintain the overlay network, each Nebula
host must communicate with the lighthouse and other overlay hosts (underlay traffic). By default, overlay hosts that
route `0.0.0.0/0` into the Nebula tunnel also send Nebula's underlay traffic into the same tunnel, triggering the
routing loop.

Here are the strategies to prevent routing loops on Linux, macOS, and Windows.

#### Linux

On Linux, Nebula supports [listen.so_mark](/docs/config/listen/#listenso_mark), which assigns an `SO_MARK` socket mark
to all of Nebula's outgoing underlay UDP traffic. By marking the packets, you can divert general system traffic through
the Nebula tunnel via policy routing while allowing Nebula's underlay traffic to bypass the tunnel.

To enable marking underlay packets, add this option to your config:

```yaml
listen:
  so_mark: 0x6EB
```

After that, configure policy routing by creating a custom routing table for internal overlay network traffic. In that
table, set the default route via the internet gateway host and add policy rules to bypass marked underlay packets:

```sh
ip route replace default via 10.0.0.5 dev nebula1 table 4242
ip rule add pref 5000 table main suppress_prefixlength 0
ip rule add pref 5001 not fwmark 0x6EB table 4242
```

For more information, see [listen.so_mark](/docs/config/listen/#listenso_mark) and
[slackhq/nebula#1837](https://github.com/slackhq/nebula/issues/1837).

#### macOS and Windows

To avoid routing loops on macOS and Windows, you need to do two things.

Configure routing all traffic `0.0.0.0/0` to the Nebula tunnel. To avoid conflicts with your system's default gateway
route, split `0.0.0.0/0` into two more specific `/1` routes that will take precedence over the default gateway:

```yaml
unsafe_routes:
  - route: 0.0.0.0/1
    via: 10.0.0.5
  - route: 128.0.0.0/1
    via: 10.0.0.5
```

Bypass underlay traffic by manually adding explicit static routes in your operating system's routing table for the
public IPs of the lighthouse and the internet gateway host. If you need access to other overlay hosts, you can also add
routes for their public IPs. Note that manually maintaining static routes is generally impractical for hosts with
dynamic IPs and rarely possible for hosts behind NAT.
